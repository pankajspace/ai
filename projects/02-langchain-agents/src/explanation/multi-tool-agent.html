🛠️ Multi-Tool Agent#

🛠️ Multi-Tool Agent gives the same LangChain agent four tools — get_weather, add, multiply and get_population — and lets the model pick zero, one or several for each question.

Unit 1

How It Works#

The idea behind the demo, the request it sends and the function calls that answer it.

1

Concept#

Multi-Tool Agent scales the LangChain agent up from one tool to a toolkit of four distinct capabilities: get_weather(city), add(a, b), multiply(a, b), and get_population(city). With multiple tools on the table, the LLM must act as a semantic router and planner — deciding not just whether to use a tool, but which combination of tools satisfies a compound user request.

When asked a multi-part question such as "What's the weather in Tokyo, and what is 12 times 12?", the agent dispatches both get_weather(city="Tokyo") and multiply(a=12, b=12), collects both tool outputs, and synthesizes a single coherent answer. Conversely, if asked "Who wrote Romeo and Juliet?", it recognizes that none of the four tools apply and answers directly.

2

Theory#

1. Semantic Tool Selection Across a Toolkit

When multiple tools are registered in tools=[get_weather, add, multiply, get_population], every LLM request includes the JSON Schema definitions for all four functions. The model compares the user's intent against each tool's name, parameter types, and docstring to pick the right match without any hardcoded if/elif routing logic in Python.

2. Parallel Multi-Tool Calls in a Single Turn

Modern tool-calling models can emit multiple items in a single tool_calls array when sub-questions are independent (for example, looking up Tokyo's weather and multiplying two numbers at the same time). LangChain executes all requested tools, appends a ToolMessage for each one, and feeds the combined observations back to the model in the next step.

3. Atomic, Single-Purpose Tool Design

Notice that add(a, b) and multiply(a, b) are separate, narrowly typed functions rather than one vague do_stuff(query: str) function. Narrow, well-named tools with unambiguous parameter signatures dramatically reduce argument-extraction errors and can be composed freely by the agent.

4. Guarding Against Lazy Tool Summaries in the System Prompt

Smaller or faster models sometimes see a tool output in the conversation history and reply vaguely (e.g., "I have fetched the weather and calculation for you above"), forgetting that the end user cannot see raw ToolMessage blocks. The system prompt explicitly instructs: "Always state the final result clearly and completely in your answer."

Code explanation#

This demo is implemented across two backend Python files in src/python/ that power the Multi-Tool Agent card in the frontend UI (src/index.html and src/js/main.js).

1. Purpose of each file

  • src/python/05_langchain_multi_tools.py: Defines three distinct domain tools (calculator, get_weather, and LookupBook), binds them to ChatOpenAI, and runs a multi-step agent loop that can invoke multiple tools across turns to answer compound prompts.
  • src/python/app.py: The Flask application and /api Blueprint that validates the incoming HTTP payload, dynamically imports 05_langchain_multi_tools.py, and returns the final answer along with a structured trace of every tool call.

2. Key entities in src/python/05_langchain_multi_tools.py

  • MultiToolRequest, ToolCallEntry, & MultiToolResponse: Pydantic schemas defining the input prompt and the output structure containing answer and tool_calls (a list of {tool, args, result} trace items).
  • CITIES & BOOKS dictionaries: Deterministic in-memory knowledge tables holding weather data for five cities (Mumbai, Delhi, Bengaluru, London, Tokyo) and metadata for three classic software engineering books (Clean Code, The Pragmatic Programmer, Designing Data-Intensive Applications).
  • Three LangChain Tools (Step ①):
    • @tool def calculator(expression: str) -> str: Evaluates arithmetic expressions using Python's eval() with __builtins__ stripped out and only the math module exposed.
    • @tool def get_weather(city: str) -> str: Looks up the normalized city name in CITIES and returns a formatted temperature and condition string.
    • @tool def LookupBook(title: str) -> str: Looks up a book title in BOOKS and returns its author, publication year, and summary.
  • TOOLS & TOOL_MAP: TOOLS lists the three tool objects for model.bind_tools(TOOLS), while TOOL_MAP = {t.name: t for t in TOOLS} indexes them by name for $O(1)$ dispatch when the LLM requests a tool call.
  • run_multi_tool_agent(prompt: str) -> tuple[str, list[ToolCallEntry]] (Steps ②–③):
    • Binds all three tools to ChatOpenAI(model="gpt-4o-mini", temperature=0) and initializes the messages list with a SystemMessage and the user's HumanMessage.
    • Runs a bounded loop (for _ in range(6):) that invokes the LLM and appends the returned AIMessage to messages.
    • If ai.tool_calls is empty, the model has finished gathering facts and its ai.content is returned alongside the trace list.
    • Otherwise, for each tool call in ai.tool_calls, it dispatches TOOL_MAP[call["name"]].invoke(call["args"]), records a ToolCallEntry in trace, and appends a ToolMessage(content=str(result), tool_call_id=call["id"]) so the LLM sees all tool results on the next iteration.

3. Key entities in src/python/app.py

  • load_module(name, filename): Dynamically loads 05_langchain_multi_tools.py on demand.
  • multi_tool_service() (POST /api/multi-tool): Verifies OPENAI_API_KEY, validates the prompt field via read_json_field(), executes mod.run_multi_tool_agent(prompt), and serializes each ToolCallEntry via t.model_dump() into the JSON response.

4. How the components connect end-to-end

  1. The user submits a compound question in the browser UI, triggering POST /api/multi-tool with {"prompt": "..."}.
  2. multi_tool_service() in app.py validates the request and calls run_multi_tool_agent(prompt) in 05_langchain_multi_tools.py.
  3. ChatOpenAI.bind_tools(TOOLS) inspects the JSON schemas of calculator, get_weather, and LookupBook (derived from their type hints and docstrings) and emits one or more structured tool_calls.
  4. The Python loop executes each requested tool via TOOL_MAP, logs the call in trace, and feeds the ToolMessage outputs back to the LLM until it produces a final natural-language answer.
  5. app.py returns {"answer": answer, "tool_calls": [...]} to the browser, which renders both the tool execution badges and the final synthesized response.

Langchain Version V1 - Agents (multiple tools + visible tool calls)

"""
Langchain Version V1 - Agents (multiple tools + visible tool calls)

Teaching idea: give the agent SEVERAL tools, then SHOW what it does internally.
For each question the agent: reads the tools -> decides which to call ->
calls it -> reads the result -> writes a final answer. The step trace below
makes that loop visible so students can see the function calls happen.

NOTE on the OpenAI 429 ('insufficient_quota'): billing state, not a bug.
PROVIDER="groq" (free) keeps you teaching without OpenAI credits.
"""

import os

from dotenv import find_dotenv, load_dotenv
from langchain.agents import create_agent
from langchain_openai import ChatOpenAI
from pydantic import BaseModel

# ---------------------------------------------------------------------------
# Configuration & Provider Selection
# ---------------------------------------------------------------------------
# Load API keys and model names from .env
load_dotenv(find_dotenv())

# Pick a provider: "groq" (free + fast), "gemini" (free tier) or "openai" (needs billing).
# Its settings are read from <PROVIDER>_MODEL / <PROVIDER>_API_KEY / <PROVIDER>_BASE_URL in .env
# (get keys at https://console.groq.com or https://aistudio.google.com)
PROVIDER = "groq"
prefix = PROVIDER.upper()


# ---------------------------------------------------------------------------
# Request & Response Schemas (Pydantic)
# ---------------------------------------------------------------------------
class MultiToolAgentRequest(BaseModel):
    """Input payload for multi-tool LangChain agent queries."""

    message: str = "What's the weather in Tokyo, and what is 12 times 12?"


class MultiToolAgentResponse(BaseModel):
    """Output payload containing the final response and tool call indicator."""

    message: str
    response: str
    tool_called: bool


# ---------------------------------------------------------------------------
# Tools
#   1. Type hints (city: str)  -> tell the model what arguments to pass
#   2. The docstring           -> tells the model WHEN to use this tool
# ---------------------------------------------------------------------------
def get_weather(city: str) -> str:
    """Get the current weather for a given city."""
    return f"The weather in {city} is sunny, 28 degrees C."


def add(a: float, b: float) -> float:
    """Add two numbers together."""
    return a + b


def multiply(a: float, b: float) -> float:
    """Multiply two numbers together."""
    return a * b


def get_population(city: str) -> str:
    """Get the approximate population of a major city."""
    data = {
        "new york": "8.5 million",
        "london": "9 million",
        "bangalore": "13 million",
        "tokyo": "14 million",
    }
    return data.get(city.lower(), f"Sorry, I don't have population data for {city}.")


# ---------------------------------------------------------------------------
# Build the agent
# ---------------------------------------------------------------------------
# ① Initialize the LLM client pointed at the configured provider
#   (placeholder key avoids an import-time crash when the key is unset)
llm = ChatOpenAI(
    model=os.getenv(f"{prefix}_MODEL"),
    api_key=os.getenv(f"{prefix}_API_KEY") or "missing-key",
    base_url=os.getenv(f"{prefix}_BASE_URL") or None,
    temperature=0,
    timeout=20.0,
)

# ② Create the multi-tool LangChain agent with all 4 tools registered
agent = create_agent(
    model=llm,
    tools=[get_weather, add, multiply, get_population],
    # Tighter prompt: force the model to actually state the result so we don't
    # get vague answers like "that's the current weather".
    system_prompt=(
        "You are a helpful assistant. Use the available tools when needed. "
        "Always state the final result clearly and completely in your answer."
    ),
)


# ---------------------------------------------------------------------------
# Core Service Logic
# ---------------------------------------------------------------------------
def run_multi_tool_agent(question: str = "What's the weather in Tokyo, and what is 12 times 12?") -> tuple[str, bool]:
    """Run a user question through the multi-tool LangChain agent."""
    # ③ Invoke the multi-tool agent with the user's question
    messages = agent.invoke({"messages": [{"role": "user", "content": question}]})["messages"]

    # ④ Detect whether one or more tools were executed during the turn
    tool_called = any(m.type == "tool" for m in messages)

    # ⑤ The last message is the final synthesized answer
    return messages[-1].content, tool_called

"""Flask server for 02-langchain-agents."""

import importlib.util
import os
import sys
from pathlib import Path

from dotenv import find_dotenv, load_dotenv
from flask import Blueprint, Flask, jsonify, request
from flask_cors import CORS
from rate_limiter import check_rate_limit

load_dotenv(find_dotenv())

PATH_PREFIX = os.environ.get("PATH_PREFIX", "")
STATIC_DIR = Path(__file__).resolve().parents[1]
app = Flask(__name__, static_folder=str(STATIC_DIR))
CORS(app)

bp = Blueprint("main", __name__)

_CUR_DIR = Path(__file__).resolve().parent


def _load_service(filename: str, alias: str):
    # ① Resolve the numbered service file path and create its import spec
    file_path = _CUR_DIR / filename
    spec = importlib.util.spec_from_file_location(f"services.{alias}", file_path)
    if spec is None or spec.loader is None:
        raise ImportError(f"Cannot load module from {file_path}")
    # ② Register and execute the module so its functions can be called by routes
    mod = importlib.util.module_from_spec(spec)
    sys.modules[f"services.{alias}"] = mod
    spec.loader.exec_module(mod)
    return mod


mod_summarize = _load_service("01_langchain_summarizer.py", "langchain_summarizer")
mod_memory = _load_service("02_langchain_memory_chat.py", "langchain_memory_chat")
mod_agent = _load_service("03_agent_one_tool.py", "agent_one_tool")
mod_lc_tool = _load_service("04_langchain_one_tool.py", "langchain_one_tool")
mod_lc_multi = _load_service("05_langchain_multi_tools.py", "langchain_multi_tools")


@bp.before_request
def enforce_rate_limit():
    # ① Only rate-limit mutating POST requests
    if request.method == "POST":
        # ② Check whether this client has exceeded 30 requests per hour
        blocked, msg, retry_after = check_rate_limit(
            request, max_requests=30, window_seconds=3600
        )
        if blocked:
            # ③ Return HTTP 429 with Retry-After header when rate-limited
            resp = jsonify({"error": msg})
            resp.status_code = 429
            resp.headers["Retry-After"] = str(retry_after)
            return resp


@bp.route("/")
def index():

    html = html.replace('data-api-base=""', f'data-api-base="{PATH_PREFIX}"')

@bp.route("/api/summarize", methods=["POST"])
def summarizer_service():
    # ① Parse input text from JSON payload and reject empty strings
    data = request.get_json(force=True, silent=True) or {}
    text = (data.get("text") or data.get("message") or "").strip()
    if not text:
        return jsonify({"error": "Text cannot be empty"}), 400
    try:
        # ② Run the LangChain LCEL summarizer chain in 01_langchain_summarizer.py
        summary = mod_summarize.summarize(text)
        return jsonify({"result": summary, "summary": summary})
    except Exception as exc:
        return jsonify({"error": str(exc)}), 500


@bp.route("/api/memory-chat", methods=["POST"])
def memory_chat_service():
    # ① Parse user message and prior conversation history from JSON payload
    data = request.get_json(force=True, silent=True) or {}
    message = (data.get("message") or "").strip()
    history = data.get("history") or []
    if not message:
        return jsonify({"error": "Message cannot be empty"}), 400
    try:
        # ② Convert history dicts to ChatMessage models and run chat_with_memory()
        chat_history = [
            mod_memory.ChatMessage(**m) if isinstance(m, dict) else m
            for m in history
        ]
        reply, updated_history = mod_memory.chat_with_memory(message, chat_history)
        return jsonify({
            "result": reply,
            "response": reply,
            "history": [m.model_dump() if hasattr(m, "model_dump") else m for m in updated_history],
        })
    except Exception as exc:
        return jsonify({"error": str(exc)}), 500


@bp.route("/api/agent", methods=["POST"])
def agent_service():
    # ① Parse user query from JSON payload and reject empty messages
    data = request.get_json(force=True, silent=True) or {}
    message = (data.get("message") or "").strip()

        return jsonify({"error": "Message cannot be empty"}), 400

        # ② Run the raw OpenAI tool-calling loop in 03_agent_one_tool.py

        return jsonify({"error": str(exc)}), 500

def multi_tool_agent_service():
    # ① Parse user query from JSON payload and reject empty messages
    data = request.get_json(force=True, silent=True) or {}
    message = (data.get("message") or "").strip()
    if not message:
        return jsonify({"error": "Message cannot be empty"}), 400

    except Exception as exc:
        return jsonify({"error": str(exc)}), 500

Quick revision#

Use these numbered points to revise the core concepts behind multi-tool LangChain agents:

  1. Multi-Tool Routing by the LLM: When multiple tools are bound via model.bind_tools(TOOLS), the LLM acts as a semantic router—reading each tool's name, docstring, and parameter schema to decide which tool(s) fit each part of a user's query.
  2. Docstrings as Routing Prompts: The model never sees the Python body of a tool; clear, specific docstrings (such as listing supported cities or book titles) directly determine how accurately the LLM selects tools and formats arguments.
  3. Parallel & Sequential Tool Calling: Modern OpenAI models can emit multiple entries inside ai.tool_calls in a single turn (for independent lookups like weather + book info) or chain tools across consecutive loop iterations when a later calculation depends on an earlier lookup.
  4. TOOL_MAP Dictionary Dispatch: Indexing tools with TOOL_MAP = {t.name: t for t in TOOLS} replaces brittle if/elif chains with a clean dictionary lookup that scales to any number of registered tools.
  5. ToolMessage Correlation via tool_call_id: Every tool output must be wrapped in a ToolMessage(content=..., tool_call_id=call["id"]) so the LLM can match each result back to the specific tool_calls entry it requested.
  6. Bounded Execution Loop (range(6)): Wrapping the ReAct cycle in a fixed-ceiling loop prevents runaway token spend or infinite loops if a tool returns unexpected output.
  7. Zero Temperature for Tool Selection: Setting temperature=0 on ChatOpenAI makes tool selection and argument extraction deterministic and reliable across repeated runs.
  8. Observability via Structured Tool Traces: Recording every ToolCallEntry(tool, args, result) gives users and developers full transparency into how the agent arrived at its final answer rather than treating the agent as a black box.
