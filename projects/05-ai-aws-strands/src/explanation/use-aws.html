Unit 1

How It Works#

The idea behind the demo, the request it sends and the function calls that answer it.

1

Concept#

Natural Language AWS Agent (use_aws) equips a Strands agent with the prebuilt use_aws tool from strands_tools, which acts as a universal bridge between natural-language requests and the AWS SDK for Python (boto3).

When you ask "List all S3 buckets in my account" or "Describe my EC2 instances in us-east-1", the agent translates your plain-English question into a structured use_aws invocation specifying service_name (e.g., "s3"), operation_name (e.g., "list_buckets"), parameters, region, and a human-readable label. The tool executes the real boto3 API call against the configured AWS account and returns the response for the agent to summarize.

2

Theory#

1. One Meta-Tool vs. Thousands of Individual API Tools

AWS has over 200 services and tens of thousands of API actions. Registering a separate @tool function for every AWS operation would blow past any LLM's context window. Instead, use_aws is a single parameterized meta-tool: the model relies on its pretraining knowledge of boto3 client names and snake_case operation names to fill in service_name, operation_name, and parameters dynamically.

2. IAM Least Privilege Is the True Security Boundary

Prompt instructions like "Please do not delete anything" are soft guardrails that can be bypassed by prompt injection or model mistakes. When giving an agent cloud access, the hard security boundary is the AWS IAM Policy attached to the credentials or instance role — always scope agent credentials to read-only permissions (ReadOnlyAccess or specific List* / Describe* actions).

3. Built-In Consent Refusal for Mutating & Sensitive Calls

As a second layer of defense, use_aws inspects the operation name before calling boto3. Mutating operations (such as create_*, delete_*, terminate_*, put_*) and sensitive secret reads (such as secretsmanager.get_secret_value) trigger an interactive confirmation prompt, which automatically fails closed when running inside a non-interactive web server process.

Code explanation#

1. Purpose of Each File

  • src/python/09_use_aws.py — Defines the Natural Language AWS Agent service: imports the prebuilt use_aws meta-tool from strands_tools, configures the Strands Agent with a cloud-management system prompt, runs plain-English AWS queries against real AWS APIs via boto3, and records every executed AWS operation.
  • src/python/app.py — Loads 09_use_aws.py dynamically as s_aws, enforces rate limiting on POST requests, and exposes POST /api/use-aws via use_aws_route().
  • src/index.html + src/js/main.js — Renders the ☁️ AWS Cloud Assistant card, sends the user's plain-English AWS prompt to POST /api/use-aws with { prompt }, and displays both the summarized cloud resource report and operations_executed.

2. Pydantic Schemas, Prebuilt use_aws Tool & Agent Setup in 09_use_aws.py

  • Step ① — Environment Configuration (load_dotenv(find_dotenv())): Loads AWS credentials (AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, AWS_DEFAULT_REGION) and Bedrock model configuration from .env.
  • UseAwsRequest(BaseModel) & UseAwsResponse(BaseModel): Specify the input payload (prompt: str defaulting to "List all S3 buckets in my account") and output payload (prompt, response, and operations_executed: list[str]).
  • Step ② — Model Selection (model_id): Reads BEDROCK_MODEL_ID from the environment, defaulting to "amazon.nova-lite-v1:0".
  • Prebuilt Meta-Tool (from strands_tools import use_aws): Exposes the entire AWS SDK for Python (boto3) through a single structured tool schema accepting service_name (e.g., "s3", "sts", "dynamodb"), operation_name (e.g., "list_buckets", "get_caller_identity"), parameters (dict), region (str), and label (str).
  • Service Entry Point — run_use_aws_agent(prompt: str) -> dict:
    • Step ③: Instantiates Agent(model=BedrockModel(model_id=model_id), tools=[use_aws], system_prompt="You are an AWS assistant that helps manage cloud resources.").
    • Step ④: Calls response = agent(prompt), where Bedrock maps the user's English request to the exact boto3 service and snake_case operation name, invokes use_aws, and summarizes the returned AWS JSON.
    • Step ⑤: Extracts all "toolUse" blocks from agent.messages into operations_executed and returns {"prompt": prompt, "response": str(response), "operations_executed": tool_calls}.

3. Flask Route Handler in src/python/app.py

  • use_aws_route() (POST /api/use-aws):
    • Step ①: Parses prompt (or fallback message) from the JSON request body and returns HTTP 400 if empty.
    • Step ②: Calls s_aws.run_use_aws_agent(prompt), copies res["response"] to res["result"], and returns the JSON payload (or HTTP 500 on error).

4. End-to-End Walkthrough: How All Entities Connect

  1. The user clicks Run on the ☁️ AWS Cloud Assistant card in src/index.html; src/js/main.js sends POST /api/use-aws with {"prompt": "List all S3 buckets in my account"}.
  2. Flask's enforce_rate_limit() middleware verifies the client is within the 30-requests/hour limit and dispatches the request to use_aws_route().
  3. use_aws_route() validates prompt and calls s_aws.run_use_aws_agent(prompt) in 09_use_aws.py.
  4. run_use_aws_agent() initializes a Strands Agent with BedrockModel(model_id=model_id) and tools=[use_aws].
  5. Calling agent(prompt) sends the prompt and the use_aws tool specification to Amazon Bedrock via the Converse API.
  6. Bedrock translates "List all S3 buckets in my account" into a toolUse block calling use_aws(service_name="s3", operation_name="list_buckets", parameters={}, region="us-east-1", label="List all S3 buckets").
  7. Inside use_aws, the tool verifies that list_buckets is a non-mutating read operation, creates a boto3.client("s3") using the server's IAM credentials, executes client.list_buckets() against AWS, and returns the bucket list in a toolResult block.
  8. Bedrock formats the bucket names and creation dates into a clean answer, run_use_aws_agent() collects operations_executed from agent.messages, and app.py returns the JSON response to the browser.

Natural Language Cloud / AWS Agent Service.

"""Natural Language Cloud / AWS Agent Service.

Demonstrates `use_aws` natural language cloud operations:
1. The prebuilt `use_aws` tool from `strands_tools` exposes the whole AWS API (via boto3) to the agent.
2. The agent translates a plain-English request into service_name + operation_name + parameters.
3. Calls run against the real AWS account of the configured credentials, so give them a read-only IAM policy.
   Mutating calls and secret reads ask for confirmation, which is refused in the server (no terminal).
"""

import os

from dotenv import find_dotenv, load_dotenv
from pydantic import BaseModel
from strands import Agent
from strands.models.bedrock import BedrockModel
from strands_tools import use_aws

# ① Load AWS credentials and Bedrock configuration from .env
load_dotenv(find_dotenv())


class UseAwsRequest(BaseModel):
    """Input payload for Use AWS Agent."""

    prompt: str = "List all S3 buckets in my account"


class UseAwsResponse(BaseModel):
    """Output payload from Use AWS Agent."""

    prompt: str
    response: str
    operations_executed: list[str]


# ② Resolve the target Bedrock model identifier
model_id = os.getenv("BEDROCK_MODEL_ID", "amazon.nova-lite-v1:0")


def run_use_aws_agent(prompt: str = "List all S3 buckets in my account") -> dict:
    """Run the Use AWS Agent."""
    # ③ Initialize the Strands Agent with the prebuilt use_aws tool and cloud assistant system prompt
    agent = Agent(
        model=BedrockModel(model_id=model_id),
        tools=[use_aws],
        system_prompt="You are an AWS assistant that helps manage cloud resources.",
    )

    # ④ Execute the natural language AWS request
    response = agent(prompt)

    # ⑤ List the AWS API operations the agent chose (service, operation, parameters)
    tool_calls = [
        f"{block['toolUse']['name']}({block['toolUse']['input']})"
        for message in agent.messages
        for block in message["content"]
        if "toolUse" in block
    ]

    return {"prompt": prompt, "response": str(response), "operations_executed": tool_calls}

def _load_service(filename: str, alias: str):
    # ① Resolve the numbered service file path and create its import spec
    file_path = _CUR_DIR / filename
    spec = importlib.util.spec_from_file_location(f"services.{alias}", file_path)
    if spec is None or spec.loader is None:
        raise ImportError(f"Cannot load module from {file_path}")
    # ② Register and execute the module so its functions can be called by routes
    mod = importlib.util.module_from_spec(spec)
    sys.modules[f"services.{alias}"] = mod
    spec.loader.exec_module(mod)
    return mod

@bp.before_request
def enforce_rate_limit():
    # ① Only rate-limit mutating POST requests
    if request.method == "POST":
        # ② Check whether this client has exceeded 30 requests per hour
        blocked, msg, retry_after = check_rate_limit(
            request, max_requests=30, window_seconds=3600
        )
        if blocked:
            # ③ Return HTTP 429 with Retry-After header when rate-limited
            resp = jsonify({"error": msg})
            resp.status_code = 429
            resp.headers["Retry-After"] = str(retry_after)
            return resp

Key AI concepts, architectural patterns, and practical takeaways from this demo.

Quick revision#

Use this numbered checklist to review the core concepts, boto3 meta-tool architecture, and cloud security guardrails in the ☁️ AWS Cloud Assistant demo:

  1. The Meta-Tool Pattern (use_aws): Instead of registering thousands of separate tools for 200+ AWS services (which would overflow the LLM context window), use_aws exposes a single parameterized schema (service_name, operation_name, parameters, region, label) backed by boto3.
  2. Leveraging Pretrained boto3 Knowledge: Frontier and Nova models already know boto3 service names (like "s3", "ec2", "sts") and snake_case operation names (like "list_buckets", "describe_instances") from pretraining, allowing zero-shot translation from English to AWS API calls.
  3. Hard Security Boundary via IAM Least Privilege: Because use_aws executes real API calls using the host environment's AWS credentials, the true security boundary is the IAM Policy attached to those credentials — always restrict agent roles to read-only permissions.
  4. Built-In Consent Guardrail for Mutating Calls: use_aws inspects operation_name before invoking boto3; mutating verbs (create_*, delete_*, terminate_*, put_*) and secret reads (get_secret_value) require interactive terminal confirmation, which automatically fails closed in a headless web server.
  5. Self-Documenting Calls via label: The use_aws schema requires a human-readable label argument on every call, making audit logs and UI tool traces immediately understandable alongside the raw boto3 parameters.
  6. Multi-Call Discovery & Error Recovery: If an operation requires a resource identifier (such as a bucket name or table name) or if the model supplies an invalid parameter on its first attempt, the Strands Converse loop lets the agent list resources first or self-correct based on the returned boto3 exception.
  7. Auditing Cloud Actions (operations_executed): Extracting every toolUse block from agent.messages into operations_executed gives operators full visibility into which AWS services, regions, and parameters were queried.
  8. Shared Credentials Between Bedrock and use_aws: Both BedrockModel (which calls bedrock-runtime:Converse) and use_aws (which calls target services like S3 or STS) authenticate through the standard boto3 credential chain loaded via load_dotenv() or IAM roles.
