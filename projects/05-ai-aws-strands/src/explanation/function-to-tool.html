🔌 Function to Tool#

🔌 Function to Tool turns an ordinary Python function into an agent tool with Strands' @tool decorator: check_server_status(server_url) makes a real HTTP request to the URL you mention.

Unit 1

How It Works#

The idea behind the demo, the request it sends and the function calls that answer it.

1

Concept#

Function to Tool (Website Health Checker) demonstrates how a standard Python function that performs real network I/O — checking whether a live website is reachable via requests.get(url, timeout=5) — becomes an autonomous agent capability with a single @tool decorator in AWS Strands.

When you ask "Is https://www.google.com reachable right now?", the Bedrock model reads the schema Strands generated from check_website(url: str) -> str, extracts the URL, triggers the live HTTP request from the server, inspects the returned status string (e.g., "https://www.google.com is up (status 200)"), and reports the result.

2

Theory#

1. The Three Pillars of a Strands @tool Function

When you decorate a function with @tool, Strands compiles a Bedrock Converse toolSpec from three parts of your Python definition:

  1. Decorator (@tool): Wraps the function in a metadata descriptor that the Agent can register and invoke.
  2. Type Hints (url: str → str): Defines the JSON Schema input types so the model knows to pass a string URL.
  3. Docstring: Becomes the semantic prompt that tells the model when to call the tool and what the url parameter represents.

2. Docstrings Are Prompts (The "Does a Thing" Experiment)

The LLM never sees the body of check_website() (it cannot see that your code calls requests.get). It only sees the function name, parameter types, and docstring. If you replace the docstring with """Does a thing.""", the model loses confidence in what the tool does and frequently refuses to call it or passes malformed arguments.

3. Defensive Error Handling Inside Tools

Real-world network calls fail (DNS errors, connection timeouts, SSL errors). Wrapping requests.get(url, timeout=5) in try/except requests.RequestException as e: and returning a readable string (f"{url} is down ({e})") allows the agent to report the outage gracefully instead of crashing the Flask worker with an unhandled exception.

4. Auditing Tool Invocations via agent.messages

After agent(prompt) completes, iterating over agent.messages and extracting every content block containing a "toolUse" key lets the backend surface the exact function call and arguments (check_website({'url': ...})) in the UI.

Code explanation#

1. Core AI & Tool Components in 03_function_to_tool.py

  • Pydantic Contracts (FunctionToToolRequest & FunctionToToolResponse): Define the input question: str (defaulting to "Is the staging server running? Check https://httpbin.org/get") and output dictionary fields (question: str, response: str, tool_calls: list[str]).
  • Step ② Model Identifier (model_id): Resolves the target Bedrock model ID, defaulting to "amazon.nova-lite-v1:0".
  • @tool def check_server_status(server_url: str) -> str: Demonstrates the three building blocks that Strands inspects to generate a Bedrock Converse toolSpec:
    1. Decorator (@tool): Attaches tool specification metadata to the Python function so Strands can register and invoke it.
    2. Type Hints (server_url: str → str): Tells Strands that server_url is a required string property in the generated JSON Schema.
    3. Docstring (Args: & Returns:): Acts as the instruction manual the LLM reads to decide when to call the tool and what argument to pass. Inside the function body, a try/except requests.exceptions.RequestException block performs requests.get(server_url, timeout=5) and returns either f"Server is up. Status code: {response.status_code}" or "Server is down or unreachable" so network errors are returned cleanly as tool observations rather than crashing the agent loop.
  • run_function_to_tool_agent(question: str) -> dict:
    • Step ③: Creates a fresh Agent(model=BedrockModel(model_id=model_id), tools=[check_server_status]).
    • Step ④: Calls response = agent(question), executing the Converse tool-use cycle.
    • Step ⑤: Iterates over every message in agent.messages and every content block in message["content"], formatting any "toolUse" block as f"{block['toolUse']['name']}({block['toolUse']['input']})" and returning {"question": question, "response": str(response), "tool_calls": tool_calls}.

2. End-to-End AI Execution Walkthrough

  1. run_function_to_tool_agent(question) instantiates a Strands Agent with tools=[check_server_status]. Strands introspects the function's signature and docstring to build the Bedrock toolSpec.
  2. On Turn 1, Bedrock Nova Lite reads the user question (e.g., "Is the staging server running? Check https://httpbin.org/get") and the tool spec, extracts "https://httpbin.org/get", and returns an assistant message containing a toolUse block for check_server_status.
  3. Strands intercepts the toolUse block, calls check_server_status(server_url="https://httpbin.org/get") in Python, receives "Server is up. Status code: 200" from requests.get(), and sends a toolResult block back to Bedrock.
  4. On Turn 2, Bedrock reads the status code result and generates a natural-language confirmation.
  5. Step ⑤ extracts the toolUse record from agent.messages and returns {"question": question, "response": str(response), "tool_calls": tool_calls}.

Function-to-Tool Agent Service.

"""Function-to-Tool Agent Service.

Demonstrates converting a plain Python function into an LLM Agent Tool:
1. Decorator: `@tool` exposes the function to the agent loop.
2. Type hints: inform the agent of expected parameter and return types.
3. Docstring: guides the agent on WHEN and HOW to call the tool.
4. Tool: `check_server_status(server_url: str)` making live HTTP checks.
"""

import os

import requests
from dotenv import find_dotenv, load_dotenv
from pydantic import BaseModel
from strands import Agent, tool
from strands.models.bedrock import BedrockModel

# ① Load AWS credentials and Bedrock configuration from .env
load_dotenv(find_dotenv())


class FunctionToToolRequest(BaseModel):
    """Input payload for Function-to-Tool Agent."""

    question: str = "Is the staging server running? Check https://httpbin.org/get"


class FunctionToToolResponse(BaseModel):
    """Output payload from Function-to-Tool Agent."""

    question: str
    response: str
    tool_calls: list[str]


# ② Resolve the target Bedrock model identifier
model_id = os.getenv("BEDROCK_MODEL_ID", "amazon.nova-lite-v1:0")


@tool                                              # 1. decorator: exposes function to the agent
def check_server_status(server_url: str) -> str:   # 2. type hints: defines parameter & return types
    """Check if a server is responding by making an HTTP request.

    Args:
        server_url: The URL of the server to check

    Returns:
        A message indicating whether the server is up or down
    """                                            # 3. docstring: guides the LLM on when to call it
    try:
        # Send an HTTP GET request with a 5-second timeout and report the status code
        response = requests.get(server_url, timeout=5)
        return f"Server is up. Status code: {response.status_code}"
    except requests.exceptions.RequestException:
        # Catch network or HTTP errors and return a readable diagnostic message
        return "Server is down or unreachable"


def run_function_to_tool_agent(question: str = "Is the staging server running? Check https://httpbin.org/get") -> dict:
    """Execute the Function-to-Tool agent."""
    # ③ Initialize the Strands Agent with BedrockModel and the check_server_status tool
    agent = Agent(model=BedrockModel(model_id=model_id), tools=[check_server_status])

    # ④ Run the agent on the user question
    response = agent(question)

    # ⑤ Collect every tool call the agent made from its message history
    tool_calls = [
        f"{block['toolUse']['name']}({block['toolUse']['input']})"
        for message in agent.messages
        for block in message["content"]
        if "toolUse" in block
    ]

    return {"question": question, "response": str(response), "tool_calls": tool_calls}

# Change the docstring above to just  """Does a thing."""  and re-run.
# The agent will often STOP calling the tool.
# Why? The docstring is not a comment — it is the manual the MODEL reads
# to decide whether your tool is relevant. Vague docstring = unreliable agent.

def _load_service(filename: str, alias: str):
    # ① Resolve the numbered service file path and create its import spec
    file_path = _CUR_DIR / filename
    spec = importlib.util.spec_from_file_location(f"services.{alias}", file_path)
    if spec is None or spec.loader is None:
        raise ImportError(f"Cannot load module from {file_path}")
    # ② Register and execute the module so its functions can be called by routes
    mod = importlib.util.module_from_spec(spec)
    sys.modules[f"services.{alias}"] = mod
    spec.loader.exec_module(mod)
    return mod

@bp.before_request
def enforce_rate_limit():
    # ① Only rate-limit mutating POST requests
    if request.method == "POST":
        # ② Check whether this client has exceeded 30 requests per hour
        blocked, msg, retry_after = check_rate_limit(
            request, max_requests=30, window_seconds=3600
        )
        if blocked:
            # ③ Return HTTP 429 with Retry-After header when rate-limited
            resp = jsonify({"error": msg})
            resp.status_code = 429
            resp.headers["Retry-After"] = str(retry_after)
            return resp

Key AI concepts, architectural patterns, and practical takeaways from this demo.

Quick revision#

Keep these essential principles in mind when converting Python functions into AWS Strands agent tools:

  1. The Three Pillars of @tool: Strands builds a Bedrock Converse toolSpec from (1) the @tool decorator, (2) Python type annotations (server_url: str -> str), and (3) the function docstring.
  2. Docstrings Are Model Prompts: The LLM never sees your function's Python implementation; it relies entirely on the docstring and parameter descriptions to decide when and how to invoke the tool. Vague docstrings (like "Does a thing.") cause tool-calling failures.
  3. LLMs Do Not Execute Code Directly: When Bedrock decides to use check_server_status, it only emits a structured JSON toolUse request. The Strands Agent runtime executes the actual Python function locally and sends the output back in a toolResult block.
  4. Always Set Timeouts on External I/O: Calling requests.get(server_url, timeout=5) prevents an unresponsive upstream server from hanging the agent loop and blocking the Flask worker indefinitely.
  5. Return Diagnostic Strings Instead of Raising Exceptions: Catching requests.exceptions.RequestException and returning "Server is down or unreachable" gives the LLM a clear observation it can report to the user rather than crashing the request.
  6. Automatic URL Extraction from Natural Language: Even when the URL is embedded inside a conversational question ("Is the staging server running? Check https://httpbin.org/get"), the model isolates the exact URL string to pass as server_url.
  7. Auditing Tool Calls via agent.messages: Scanning content blocks in agent.messages for "toolUse" keys provides a complete, ordered audit trail of every tool name and input dictionary the agent invoked.
  8. Per-Request Agent Isolation: Instantiating Agent(model=..., tools=[check_server_status]) inside run_function_to_tool_agent() guarantees that each API call has an isolated message history.
