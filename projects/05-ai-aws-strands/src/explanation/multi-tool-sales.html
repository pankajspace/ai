📈 Sales Pipeline Agent#

📈 Sales Pipeline Agent gives a Strands agent three small tools — get_sales_data, analyze_sales, send_email — with no order, and the agent plans the chain itself.

Unit 1

How It Works#

The idea behind the demo, the request it sends and the function calls that answer it.

1

Concept#

Multi-Tool Sales Pipeline Agent demonstrates autonomous multi-step planning and data dependency chaining across three specialized tools: get_sales_data(quarter), analyze_sales(revenue, deals), and send_email(to, subject, body).

When given a high-level goal like "Get Q1 sales data, analyze it, and email the summary to boss@company.com", no Python code specifies the execution order. Instead, the agent inspects the tool signatures, deduces that analyze_sales requires revenue and deals numbers that only get_sales_data can provide, and chains all three tools across sequential turns until the email is dispatched.

2

Theory#

1. Implicit Dependency Resolution via Tool Signatures

How does the agent know which tool to call first? Look at the input parameters:

  1. get_sales_data(quarter: str) only needs "Q1", which is already present in the user's prompt — so the agent calls it on Turn 1.
  2. analyze_sales(revenue: float, deals: int) needs numerical metrics that were unknown until get_sales_data returned {"revenue": 125000, "deals": 42} — so the agent calls it on Turn 2 using Turn 1's output.
  3. send_email(to: str, subject: str, body: str) needs the analysis summary text from Turn 2 — so the agent calls it on Turn 3.

2. Single-Responsibility Principle for Agent Tools

A common anti-pattern is building a monolithic tool like fetch_analyze_and_email_sales(quarter, recipient). While that works for one rigid workflow, it cannot answer "Just compare Q1 and Q2 sales" without sending an unwanted email. Keeping get_sales_data, analyze_sales, and send_email atomic lets the agent recombine them for any ad-hoc query.

3. Mocking External Side Effects During Development

By returning deterministic mock data in get_sales_data and simulating SMTP delivery in send_email, you can test and verify the agent's multi-step planning sequence (via tool_sequence in the response) safely before wiring real CRM or email APIs.

Code explanation#

1. Purpose of Each File in This Demo

  • src/python/05_multi_tool_sales.py: Defines three focused @tool functions (get_sales_data, analyze_sales, send_email) and the orchestrator function run_multi_tool_sales_agent(task) that passes all three tools to a Strands Agent without hardcoding an execution sequence.
  • src/python/app.py: Dynamically loads 05_multi_tool_sales.py as s_sales and exposes POST /api/multi-tool-sales via multi_tool_sales_route().
  • src/index.html + src/js/main.js: Sends the user's pipeline task in { "task": "..." } to POST /api/multi-tool-sales and displays both the agent's final summary and the ordered tool_calls trace.

2. Classes, Three @tool Functions, and Service Logic in 05_multi_tool_sales.py

  • Step ① Environment Loading (load_dotenv(find_dotenv())): Loads AWS credentials and Bedrock configuration from .env.
  • MultiToolSalesRequest(BaseModel) & MultiToolSalesResponse(BaseModel): Pydantic schemas documenting the input task: str and output dictionary fields (task: str, response: str, tool_calls: list[str]).
  • Step ② Model Identifier (model_id): Reads BEDROCK_MODEL_ID from the environment, defaulting to "amazon.nova-lite-v1:0".
  • @tool def get_sales_data(quarter: str) -> dict: Step 1 of the implicit data chain. Accepts a quarter identifier (e.g., "Q1" or "4") and returns mock CRM metrics: {"revenue": 1250000, "deals": 47, "quarter": quarter}.
  • @tool def analyze_sales(revenue: int, deals: int, quarter: str) -> str: Step 2 of the chain. Accepts revenue: int, deals: int, and quarter: str (values discovered from get_sales_data), computes avg_deal = revenue / deals, and returns the formatted executive summary string f"Q{quarter}: ${revenue:,} revenue, {deals} deals, ${avg_deal:,.0f} avg deal size".
  • @tool def send_email(to: str, subject: str, body: str) -> str: Step 3 of the chain. Accepts the recipient address, subject line, and the summary body produced by analyze_sales, and returns f"Email sent to {to}".
  • run_multi_tool_sales_agent(task: str) -> dict:
    • Step ③: Instantiates Agent(model=BedrockModel(model_id=model_id), tools=[get_sales_data, analyze_sales, send_email]).
    • Step ④: Calls response = agent(task), allowing the agentic loop to plan and execute the three-step workflow across turns.
    • Step ⑤: Extracts every "toolUse" block from agent.messages in chronological order into tool_calls and returns {"task": task, "response": str(response), "tool_calls": tool_calls}.

3. Route Handler in app.py

  • multi_tool_sales_route() (POST /api/multi-tool-sales):
    • Step ①: Parses task (or fallback key message) from the request JSON and returns HTTP 400 if empty.
    • Step ②: Calls s_sales.run_multi_tool_sales_agent(task), copies res["response"] into res["result"], and returns the JSON payload.

4. End-to-End Execution Walkthrough

  1. The user submits "Pull last quarter's sales data and email a summary to the team"; main.js sends POST /api/multi-tool-sales.
  2. multi_tool_sales_route() in app.py validates the task and calls s_sales.run_multi_tool_sales_agent(task).
  3. On Turn 1, Bedrock inspects all three tool schemas, realizes it does not yet have revenue or deals to call analyze_sales, and invokes get_sales_data(quarter=...) first.
  4. Strands runs get_sales_data() and returns {"revenue": 1250000, "deals": 47, ...} to Bedrock.
  5. On Turn 2, Bedrock feeds those exact integers into analyze_sales(revenue=1250000, deals=47, quarter=...), receiving the formatted summary string with the $26,596 average deal size.
  6. On Turn 3, Bedrock passes that summary string into send_email(to=..., subject=..., body=...) and receives "Email sent to ...".
  7. On Turn 4, Bedrock produces the final confirmation message; Step ⑤ collects all three tool calls in order and returns the JSON payload to the browser.

Multi-Tool Sales Pipeline Agent Service.

"""Multi-Tool Sales Pipeline Agent Service.

Demonstrates autonomous multi-tool planning and chained orchestration:
1. Three tools provided without explicit execution order:
   - `get_sales_data(quarter: str)`
   - `analyze_sales(revenue: int, deals: int, quarter: str)`
   - `send_email(to: str, subject: str, body: str)`
2. The agent plans the workflow: Fetch Data -> Compute Analysis -> Dispatch Email.
3. Passes the output of each tool directly as inputs into the next step of the agentic loop.
"""

import os

from dotenv import find_dotenv, load_dotenv
from pydantic import BaseModel
from strands import Agent, tool
from strands.models.bedrock import BedrockModel

# ① Load AWS credentials and Bedrock configuration from .env
load_dotenv(find_dotenv())


class MultiToolSalesRequest(BaseModel):
    """Input payload for Multi-Tool Sales Agent."""

    task: str = "Pull last quarter's sales data and email a summary to the team"


class MultiToolSalesResponse(BaseModel):
    """Output payload from Multi-Tool Sales Agent."""

    task: str
    response: str
    tool_calls: list[str]


# ② Resolve the target Bedrock model identifier
model_id = os.getenv("BEDROCK_MODEL_ID", "amazon.nova-lite-v1:0")


@tool
def get_sales_data(quarter: str) -> dict:
    """Retrieve sales data for a specific quarter."""
    # Return mock quarterly revenue and closed deal count
    return {"revenue": 1250000, "deals": 47, "quarter": quarter}


@tool
def analyze_sales(revenue: int, deals: int, quarter: str) -> str:
    """Calculate key metrics from sales data."""
    # Compute average deal size and format the executive summary string
    avg_deal = revenue / deals
    return f"Q{quarter}: ${revenue:,} revenue, {deals} deals, ${avg_deal:,.0f} avg deal size"


@tool
def send_email(to: str, subject: str, body: str) -> str:
    """Send an email message."""
    # Simulate dispatching the summary email to the target recipient
    return f"Email sent to {to}"


def run_multi_tool_sales_agent(
    task: str = "Pull last quarter's sales data and email a summary to the team",
) -> dict:
    """Run the Multi-Tool Sales Agent."""
    # ③ Initialize the Strands Agent with all three sales pipeline tools (no order given)
    agent = Agent(
        model=BedrockModel(model_id=model_id),
        tools=[get_sales_data, analyze_sales, send_email],
    )

    # ④ Execute the multi-step task (get_sales_data -> analyze_sales -> send_email)
    response = agent(task)

    # ⑤ Collect the tool calls in the order the agent made them
    tool_calls = [
        f"{block['toolUse']['name']}({block['toolUse']['input']})"
        for message in agent.messages
        for block in message["content"]
        if "toolUse" in block
    ]

    return {"task": task, "response": str(response), "tool_calls": tool_calls}


# RULE OF THUMB: build focused, single-purpose tools.
# One mega-tool that does everything is harder to maintain, harder for the
# agent to reason about, and impossible to reuse elsewhere.

def _load_service(filename: str, alias: str):
    # ① Resolve the numbered service file path and create its import spec
    file_path = _CUR_DIR / filename
    spec = importlib.util.spec_from_file_location(f"services.{alias}", file_path)
    if spec is None or spec.loader is None:
        raise ImportError(f"Cannot load module from {file_path}")
    # ② Register and execute the module so its functions can be called by routes
    mod = importlib.util.module_from_spec(spec)
    sys.modules[f"services.{alias}"] = mod
    spec.loader.exec_module(mod)
    return mod

@bp.before_request
def enforce_rate_limit():
    # ① Only rate-limit mutating POST requests
    if request.method == "POST":
        # ② Check whether this client has exceeded 30 requests per hour
        blocked, msg, retry_after = check_rate_limit(
            request, max_requests=30, window_seconds=3600
        )
        if blocked:
            # ③ Return HTTP 429 with Retry-After header when rate-limited
            resp = jsonify({"error": msg})
            resp.status_code = 429
            resp.headers["Retry-After"] = str(retry_after)
            return resp

Quick revision#

Review these key architectural lessons on multi-tool planning and sequential orchestration in AWS Strands:

  1. Autonomous Multi-Step Planning: You pass tools=[get_sales_data, analyze_sales, send_email] in any order, and the LLM plans the execution sequence dynamically based on what data each tool requires and produces.
  2. Implicit Data Dependency Resolution: Because analyze_sales(revenue: int, deals: int, quarter: str) requires revenue and deals that are not in the user's prompt, the agent deduces it must call get_sales_data(quarter) first.
  3. Single-Responsibility Tool Design: Splitting data retrieval (get_sales_data), computation (analyze_sales), and side-effect delivery (send_email) into atomic tools makes each tool reusable across arbitrary combinations of user requests.
  4. Why Mega-Tools Fail in Production: A single monolithic function that fetches, analyzes, and emails in one step cannot answer read-only questions (like "What was Q1 revenue?") without triggering unwanted side effects.
  5. Multi-Turn State Accumulation: Across the 3 tool turns, agent.messages accumulates every assistant toolUse request and user-role toolResult observation so the model has full context when composing the email body.
  6. Safe Side-Effect Mocking: Simulating SMTP delivery inside send_email() allows end-to-end verification of the agent's planning logic before connecting production email credentials.
  7. Chronological Execution Trace (tool_calls): Iterating through agent.messages in order produces the exact step-by-step sequence (get_sales_data → analyze_sales → send_email) for observability and UI display.
