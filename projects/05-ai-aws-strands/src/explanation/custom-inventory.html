📦 Custom Inventory Tool#

Unit 1

How It Works#

The idea behind the demo, the request it sends and the function calls that answer it.

1

Concept#

Custom Inventory Tool Agent shows how to bridge an LLM's general language understanding with proprietary enterprise data (such as SKU catalogs, stock levels, and warehouse locations) that no public model could ever know from pretraining.

The service defines @tool def check_inventory(product_id: str) -> str backed by an internal SKU dictionary (PROD-123 Wireless Mouse, PROD-456 USB-C Cable, PROD-789 Laptop Stand). When you ask about one or more product IDs, the Bedrock agent extracts each SKU, invokes check_inventory(), and turns the returned stock status into a clear customer-ready answer.

2

Theory#

1. Bridging the Knowledge Cutoff & Private Data Gap

Foundation models are trained on public internet text up to a fixed cutoff date; they have zero visibility into your company's internal SKUs (PROD-123) or live stock counts. Exposing a read-only lookup function via @tool gives the model on-demand access to authoritative internal state without fine-tuning or stuffing the entire catalog into the prompt.

2. Google-Style Args: Docstrings for Parameter Guidance

Strands parses the Args: block inside the function's docstring: product_id: The product ID to check (e.g., "PROD-123"). Including a concrete format example ("PROD-123") inside the parameter description teaches the model to normalize user inputs (such as "product 123" or "PROD-123") into the exact string pattern the backend expects.

3. Graceful Handling of Unknown Identifiers

When a user asks about a non-existent SKU like PROD-999, the tool does not raise a Python KeyError. Instead, it returns a clear domain message: "Product PROD-999 not found in inventory". Returning structured, human-readable not-found messages lets the LLM inform the user politely rather than crashing or hallucinating.

4. Drop-In Backend Replacement

Because the agent only interacts with the function signature and return string of check_inventory(product_id), swapping the in-memory dictionary for a PostgreSQL SELECT query or a Shopify REST API call requires zero changes to the agent setup.

    • Mock Inventory Catalog: Defines inventory = {"PROD-123": 15, "PROD-456": 0, "PROD-789": 8} representing an internal domain data store.

    • Step ③: Instantiates Agent(model=BedrockModel(model_id=model_id), tools=[check_inventory]).
    • Step ④: Executes response = agent(question) through the Strands agent loop.
    • Step ⑤: Extracts every "toolUse" block from agent.messages into tool_calls and returns {"question": question, "response": str(response), "tool_calls": tool_calls}.

2. End-to-End AI Execution Walkthrough

  1. run_custom_inventory_agent(question) creates a fresh Strands Agent registered with check_inventory and calls agent(question) (e.g., for "Is PROD-123 in stock?").
  2. On Turn 1, Bedrock Nova Lite inspects the tool schema, extracts product_id="PROD-123", and emits a toolUse block.
  3. Strands invokes check_inventory("PROD-123") in Python, which looks up "PROD-123" in inventory, finds 15, and returns "Product PROD-123 is in stock. We have 15 units available." in a toolResult block.
  4. On Turn 2, Bedrock reads the tool output and writes a natural-language reply confirming 15 units are available.
  5. Step ⑤ records check_inventory({'product_id': 'PROD-123'}) in tool_calls and returns {"question": question, "response": str(response), "tool_calls": tool_calls}.

Custom Inventory Tool Agent Service.

"""Custom Inventory Tool Agent Service.

Demonstrates building domain-specific custom tools:
1. Simulates an internal proprietary system or inventory database.
2. Custom tool `check_inventory(product_id: str)` with strict typing & docstrings.
3. Natural language query resolution against mock product inventory.
"""

import os

from dotenv import find_dotenv, load_dotenv
from pydantic import BaseModel
from strands import Agent, tool
from strands.models.bedrock import BedrockModel

# ① Load AWS credentials and Bedrock configuration from .env
load_dotenv(find_dotenv())


class CustomInventoryRequest(BaseModel):
    """Input payload for Custom Inventory Agent."""

    question: str = "Is PROD-123 in stock?"


class CustomInventoryResponse(BaseModel):
    """Output payload from Custom Inventory Agent."""

    question: str
    response: str
    tool_calls: list[str]


# ② Resolve the target Bedrock model identifier
model_id = os.getenv("BEDROCK_MODEL_ID", "amazon.nova-lite-v1:0")


@tool
def check_inventory(product_id: str) -> str:
    """Check if a product is in stock.

    Args:
        product_id: The product ID to check (e.g., "PROD-123")
    """
    # Define the mock product inventory catalog (replace with a real DB query in production)
    inventory = {
        "PROD-123": 15,
        "PROD-456": 0,
        "PROD-789": 8,
    }

    # Look up the available unit count for the requested SKU
    quantity = inventory.get(product_id, 0)

    # Return a human-readable stock status message
    if quantity > 0:
        return f"Product {product_id} is in stock. We have {quantity} units available."
    else:
        return f"Product {product_id} is currently out of stock."


def run_custom_inventory_agent(question: str = "Is PROD-123 in stock?") -> dict:
    """Run the Custom Inventory Agent."""
    # ③ Initialize the Strands Agent with BedrockModel and the custom check_inventory tool
    agent = Agent(model=BedrockModel(model_id=model_id), tools=[check_inventory])

    # ④ Run the agent on the inventory question
    response = agent(question)

    # ⑤ Collect every tool call the agent made from its message history
    tool_calls = [
        f"{block['toolUse']['name']}({block['toolUse']['input']})"
        for message in agent.messages
        for block in message["content"]
        if "toolUse" in block
    ]

    return {"question": question, "response": str(response), "tool_calls": tool_calls}

def _load_service(filename: str, alias: str):
    # ① Resolve the numbered service file path and create its import spec
    file_path = _CUR_DIR / filename
    spec = importlib.util.spec_from_file_location(f"services.{alias}", file_path)
    if spec is None or spec.loader is None:
        raise ImportError(f"Cannot load module from {file_path}")
    # ② Register and execute the module so its functions can be called by routes
    mod = importlib.util.module_from_spec(spec)
    sys.modules[f"services.{alias}"] = mod
    spec.loader.exec_module(mod)
    return mod

@bp.before_request
def enforce_rate_limit():
    # ① Only rate-limit mutating POST requests
    if request.method == "POST":
        # ② Check whether this client has exceeded 30 requests per hour
        blocked, msg, retry_after = check_rate_limit(
            request, max_requests=30, window_seconds=3600
        )
        if blocked:
            # ③ Return HTTP 429 with Retry-After header when rate-limited
            resp = jsonify({"error": msg})
            resp.status_code = 429
            resp.headers["Retry-After"] = str(retry_after)
            return resp

Quick revision#

Use these takeaways to review how custom Strands tools connect foundation models to proprietary enterprise data:

  1. Overcoming Pretraining Knowledge Boundaries: Public LLMs have zero visibility into private SKU catalogs or real-time warehouse counts; custom @tool functions give the model on-demand, read-only access to authoritative internal records.
  2. Format Examples in Parameter Docstrings: Including (e.g., "PROD-123") inside the Args: docstring for product_id guides the LLM to normalize user queries into the exact identifier format expected by the database.
  3. Defensive Lookups with dict.get(): Using inventory.get(product_id, 0) prevents unhandled KeyError exceptions when a user asks about an unknown or mistyped SKU.
  4. Clear Domain Status Strings: Returning explicit natural-language status messages ("Product PROD-123 is in stock. We have 15 units available." vs. "...currently out of stock.") eliminates ambiguity during the LLM's observation step.
  5. Clean Separation of Interface and Storage: Because the agent only sees the signature and docstring of check_inventory(product_id: str) -> str, replacing the mock dictionary with a live SQL or ERP API call requires zero changes to the agent configuration.
  6. Multi-SKU Fan-Out Support: If a user asks about two products in one question (e.g., "Check PROD-123 and PROD-456"), the agent automatically invokes check_inventory twice and compares both results in its reply.
  7. Complete Tool-Use Audit Trail: Extracting toolUse blocks from agent.messages lets the API caller verify which SKUs were queried during the turn.
