Putting it together: tool calling

  1. User asks: "What's the score in India vs WI?"
  2. App sends the question + the tool menu cards → to the AI model
  3. Model replies: "Please call get_live_score with teams='India vs West Indies'"
  4. App actually calls the cricket API → gets "287/6"
  5. App sends that result back to the model
  6. Model replies: "India scored 287/6. West Indies need 90 off 70 balls."

The model is the brain that decides. Your app is the hands that do.

MCP = Model Context Protocol

Model

The AI model.

Context

The extra information we give it, like today's score from a tool.

Protocol

Agreed rules for talking. Like HTTP for browsers. Like UPI for payments.

An agreed set of rules for how AI apps talk to tools.

Introduced by Anthropic (the company behind Claude) in late 2024 as an open standard. Most big AI players support it today.

With MCP

  • Each tool is wrapped once as an MCP server.
  • Each AI app learns MCP once as an MCP client.
  • Any client can talk to any server. Done.
Same 3 apps and 4 tools. How many integrations now?
3 + 4 = 7
And adding the highlights tool?
Just 1. ✨
With MCP: M apps + N tools = M + N integrations 10 + 50 = 60 (instead of 500) The tool is described ONCE in MCP's format. Each app converts it for its provider with one tiny function. You'll see it in the demo: to_openai_format

How do client and server talk? Like a phone call ☎️

They send JSON messages. The format is called JSON-RPC: "please run this method, with these parameters".

  1. initialize — "Hello, I'm the client. Which version do you speak?" (handshake)
  2. tools/list — "What all can you do?" (the menu card)
  3. tools/call — "Please run get_live_score with teams='India vs WI'" (the order)

You'll literally see these 3 steps in our live demo.

Bonus trap
If MCP is so similar to REST, why not just give the AI our REST API directly? Why invent MCP at all?
FOR ONE API, YOU COULD. BUT…Every REST API has a different shape. Someone hand-writes a menu card + glue code for each one. That's the integration mess again — back to M × N.

MCP doesn't replace your REST API. The MCP server often just calls it inside.

AI app → MCP (one standard shape) → MCP server → your existing REST API

How does the message travel? Two roads.

🏠

stdio

Server on the same machine. Like an intercom inside your house. The client starts the server as a child process; they talk via stdin/stdout. No network, no ports.

🌐

Streamable HTTP

Server on a remote machine, at a URL. Like a phone call across the city. Uses Server-Sent Events (SSE) so the server can also push messages back.

Trap 10
Your MCP server sends progress updates. On your laptop with stdio — perfect. You deploy it with HTTP, behind a load balancer, 10 instances, and turn on stateless mode to scale. Will progress updates still work?
NO — AND IT FAILS SILENTLYNo ongoing session → no channel to push messages. Tool calls still work, so it looks fine. Progress and logs just quietly stop.

Test on the same transport you deploy on. 😄

Three kinds of checks, cheapest first

1 · Code checks

Valid JSON? Contains "287"? Called get_live_score? Under 100 words? If code can check it, use code.

2 · Compare with a reference

Two moments to evaluate

🧪

Offline evals

Before release. A fixed test set, run on every change (new prompt, new model, new tool) — like your test suite in CI. Like a board exam.

📈

Online evals

After release. Watch real users: thumbs down, complaints, slow answers, rising bills. Like Flipkart customer reviews.

Our evals score 100% today. Are we done forever?
NOModels get updated, users ask new things. Every real bug → add it to the test set, like a regression test.

Remember "garbage in, garbage out"? Evals catch that garbage before your users do.

What we learnt today

Tools

A model is frozen at its knowledge cutoff. A tool = a function in our code + a menu card. The model asks; our app does.

MCP

The UPI of AI tools. One standard → M + N, not M × N. Like REST, plus discovery and one shape.

Inside MCP

Host → Client (one per server) → Server. Tools: model decides · Resources: app · Prompts: user. stdio or HTTP.

Evals

Code checks → reference → LLM judge. Offline + online. Your eval can lie: write strong checks, keep adding real failures.
